# ADR-001: Capas simples para persistencia; el seam de notificacion ya cubre el proximo cambio conocido

## Estado: Aceptado — 2026-11-08

## Contexto
Tras integrar Chain of Responsibility, Strategy y Observer sobre el sistema de solicitudes de reembolso, corresponde decidir si el proyecto debe migrar a arquitectura Hexagonal completa (puertos e interfaces intermedias para persistencia y notificacion) o mantenerse en capas simples. No existe hoy ningun plan de cambiar el motor de base de datos. Contabilidad si anuncio, para el proximo trimestre, una integracion por API externa para el pago de solicitudes aprobadas.

## Decision
Se mantiene arquitectura en capas simples para la persistencia: SolicitudReembolsoService sigue dependiendo directamente de RepositorioSolicitudesJpa, sin una interfaz de puerto intermedia. Un puerto de persistencia hoy seria una abstraccion especulativa (YAGNI) sin ningun caso de uso que lo requiera. Para la notificacion no se introduce ningun cambio: ObservadorCambioEstado ya es el seam necesario, y NotificadorContabilidad puede reemplazar su implementacion interna por una llamada a la API externa el proximo trimestre sin modificar SolicitudReembolsoService ni los demas observadores.

## Consecuencias
Positivas:
- No se agregan interfaces ni mappers de persistencia sin un caso de uso real que los justifique.
- El unico cambio de infraestructura con fecha conocida (integracion de Contabilidad) ya tiene su punto de extension listo.

Negativas:
- Si en el futuro se necesita cambiar de motor de base de datos, el puerto de persistencia debera introducirse retroactivamente; se acepta esa deuda tecnica de forma consciente.
- Un revisor que espere simetria total (puertos en todas las dependencias externas) puede interpretar la asimetria como inconsistencia si no lee este ADR.
